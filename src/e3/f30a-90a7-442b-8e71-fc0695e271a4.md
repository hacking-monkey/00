## 起因

前几天写了个函数，签名里有个 `[*]T`。函数体里解引用了它，崩了。

我以为是个 bug。多元素指针，指向至少一个元素，解引用第一个元素，这不是
天经地义吗？

不是。得先 `@ptrCast` 转成 `*T` 才能解引用。一个 `[*]T`，连“第一个元素可读”
都不保证。

我愣了挺久。

## 问题在哪

`*T` 是单元素指针。函数签名里写 `*T`，意思就是“这里有一个 `T`”。调用者默认可以
解引用。这是 API 边界上的承诺。

`[*]T` 是多元素指针，但现在的语义是“未知长度，包括 0”。一个 `[*]T` 可以合法地
什么都不指向。

于是就有了这个怪事：`[*]T` 能力比 `*T` 强，指针算术、索引都能做，但在 API
边界上承诺得比 `*T` 还少。你拿到一个 `[*]T`，连第一个元素能不能读都不知道。

## 空 slice 的 `.ptr` 是个坑

`[]T` 为空时，`.len == 0`，`.ptr` 可能指向零大小分配或者字面量，是个无效指针。
但类型系统不区分“空 slice 的无效指针”和“非空 slice 的有效指针”。

你很容易把 `.ptr` 传给别的函数，被调用者根本不知道它可能无效。这种隐式信息太
容易漏掉了。

如果 `[*]T` 承诺“至少一个”，那空 slice 的 `.ptr` 可以返回 `?[*]T`。
调用者必须处理零长度的情况，不变量就在类型里写明了。

## 标准库自己也不信 `[*]T`

`std.mem.span` 接受 `[*:0]T` 和 `[*c]T`，但用 `@compileError` 拒绝 `[*]T`。
没有哨兵，没有长度。

标准库自己也不知道拿一个裸 `[*]T` 怎么办。如果 `[*]T` 承诺“至少一个”，
`std.mem.span` 至少能安全读取 `ptr[0]`，而不是直接报错。

## 几个常见的反驳

> “`*T` 也不保证有效，`@ptrFromInt` 可以造无效的 `*T`。”

对。但 `*T` 的契约是“一个位置”，不是“一个有效元素”。`@ptrFromInt` 和指针算术
能绕过这个契约，但那是程序员违约，不是类型系统的错。同样，`[*]T` 应该承诺
“至少一个位置”，不是“至少一个有效元素”。两者都不保证内存有效，但都保证
“有东西可指”。

> “指针算术会产生无效指针，所以不能强制至少一个。”

指针算术在函数内部随便用。契约在 API 边界上才生效。`p += 1` 之后，契约转移到
新位置，程序员负责保证新位置有效。这和 `*T` 先 `undefined` 后赋值是一回事。
不需要运行时检查，也不妨碍指针算术。

在 LLVM IR 层面，指针算术就是 `getelementptr`，纯地址计算。不加载，不存储，
不断言有效性。只有 `load`/`store` 的时候有效性才重要。“至少一个”是解引用时的
契约，不是算术时的契约。

> “长度是带外的，类型系统无法验证。”

`[*]T` 不需要知道长度。它只需要承诺“当前位置可读”。长度信息还是程序员在带外
维护，和现在没区别。“至少一个”和“知道长度”是两件事。

> “`[*:0]T` 已经覆盖了至少一个的需求。”

`[*:0]T` 的语义核心是“以哨兵结尾”，不是“至少一个”。它保证至少一个元素只是
因为哨兵本身占一个位置，那是副产品。`[*:0]T` 解决的是“怎么知道结尾”，我关心的
是“怎么知道开头可读”。

## 现有类型的分工

- `*T`：一个位置，API 边界承诺
- `[*:0]T`：哨兵结尾，API 边界承诺
- `[*c]T`：裸地址，C 互操作，不保证有效
- `[]T`：长度加指针，安全抽象
- `[*]T`：？

按现在的设计，`[*]T` 的答案是“未知长度，可能为零，只保证非空”。但非空对
裸多元素指针几乎没有意义。你拿到一个非空地址，却不知道能不能读。所以它在 API
边界上确实比 `*T` 还弱。

## 我的主张

把 `[*]T` 的语义改成“至少一个元素”，让它成为 `*T` 在能力上的超集。

`[*]T` 能做 `*T` 能做的一切：解引用第一个元素、取地址、传参。它还能做 `*T`
不能做的：指针算术、索引、指向任意位置。所以 `[*]T -> *T` 是窄化转换，只增强
保证，应该允许隐式。`*T -> [*]T` 是拓宽转换，不应隐式存在，因为 `*T` 意味着
恰好一个，`[*]T` 意味着至少一个。

配套改动：`[]T.ptr` 对空 slice 返回 `?[*]T`，调用者加 `.?`；`std.mem.span` 对
`[*]T` 至少可以安全读取 `ptr[0]`。

## 最后说两句

Zig 官方现在不接受语言提案，这个我理解。但 `[*]T` 比 `*T` 弱这件事，是类型系统
层面的不一致，不是“用错了类型”能打发的。

C++ 也信任程序员，结果就是几十年的 UB 和安全漏洞。类型应该帮程序员表达意图、
在边界上捕捉错误，而不是在运行时当保姆。
