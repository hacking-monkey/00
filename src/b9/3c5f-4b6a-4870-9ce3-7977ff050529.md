前阵子琢磨 GC 怎么追踪 `ref`。琢磨着琢磨着跑偏了——既然 `ref` 只是个内部指针，GC 靠反查对象头保活，那我自己在栈上摆一块内存，把 MethodTable、length、字符数据全按 string 规则填好，再把这块内存解释成 string 引用，.NET 会不会被骗过去？

试了试，还真骗过去了。

```csharp
// Copyright (c) 2026 chz-cn
// SPDX-License-Identifier: Apache-2.0

#:property TargetFramework=net10.0
#:property PublishAot=false
#:property Nullable=enable
#:property ImplicitUsings=disable
#:property AllowUnsafeBlocks=true

using System;
using System.Runtime.CompilerServices;

Span<nuint> buffer = stackalloc nuint[128];
buffer.Clear ();
ref nuint obj = ref Unsafe.Add (ref buffer[0], 1);
obj = (nuint)typeof (string).TypeHandle.Value;

ref int len = ref Unsafe.As<nuint, int> (ref Unsafe.Add (ref obj, 1));
len = 5;

ref char chars = ref Unsafe.As<int, char> (ref Unsafe.Add (ref len, 1));
Unsafe.Add (ref chars, 0) = 'H';
Unsafe.Add (ref chars, 1) = 'e';
Unsafe.Add (ref chars, 2) = 'l';
Unsafe.Add (ref chars, 3) = 'l';
Unsafe.Add (ref chars, 4) = 'o';

string s;

unsafe {
  nuint ptr = (nuint)Unsafe.AsPointer (ref obj);
  s = Unsafe.As<nuint, string> (ref ptr);
}

Console.WriteLine ($"Forged string: {s}");
Console.WriteLine ($"Length: {s.Length}");

Console.WriteLine ("Triggering GC...");
GC.Collect ();

Console.WriteLine ($"Still accessible after GC: {s}");
Console.WriteLine ($"HashCode: {s.GetHashCode (StringComparison.Ordinal)}");
```

输出：

```txt
Forged string: Hello
Length: 5
Triggering GC...
Still accessible after GC: Hello
HashCode: 584091285
```

`Hello`，长度 5，GC 跑完还在，哈希也算出来。

这块栈内存现在**在运行时眼里就是一个 `class` 对象**。MethodTable 指向 `System.String`，length 在正确位置、值也对，字符数据老老实实跟在后面。GC 扫到 `s` 时没有任何理由怀疑——它看起来就是一个完全正常 string。

## 骗术拆解

GC 扫根时拿 `s` 值去堆里找对象，但它先做一步范围检查：这个地址在不在 GC 堆范围内？不在？跳过。

栈地址当然不在堆范围内。GC 看 `s` 一眼，判断“这地址不归我管”，就走。`GC.Collect()` 前后 `s` 指向栈内存纹丝不动。

`Length` 读对，因为 JIT 压根不看对象在哪，它只知道“string 的 length 在 MT 指针后面那个 int 位置”，按偏移读。写进去 `5`，读出来就是 `5`。

`GetHashCode` 算对，因为 `String.GetHashCode` 每次实时遍历字符算，不依赖堆上缓存。栈上字符是 `"Hello"`，算出来就是正常哈希值。

## 这套东西能干成什么事

**不经过分配器，凭空造 `string`。** 只要栈帧还活着，这块内存就是合法 string。`WriteLine`、`Length`、`GetHashCode`、传参给任何只读字符 BCL API，全都正常。没有 GC 分配，没有堆压力，没有写屏障。

**省掉中间字符串。** 文件路径拼接、日志消息构造、协议头组装——凡是“先拼一个临时 `string` 再传出去”的地方，都可以直接往栈上写，省掉那个中间产物。高频 IO 或遍历几十万文件场景，这个量级分配削减实打实。

**为 span 补上 `\0`。** BCL 的 IO API 只收 `string`，因为它保证 null-terminated，`Span<char>` 不保证。你在栈上捏 string 时，`length` 之后想写什么写什么，补个 `\0` 就是合法 null-terminated 缓冲区，直接喂给那些只认 `string` 的老 API。这是 span 做不到、伪造 string 能做到的事。

**布局完全由你控制。** MT 指针、length、字符数据，每一字节都是你写的。你可以精确控制这个“string”占多少内存、数据放哪、对象头什么状态。对需要极限控制内存布局的场景，这是 `span` 和普通 `string` 都给不了的自由度。

**验证了 GC 边界在哪。** 这套代码跑通本身说明 GC 根扫描确实有范围检查，堆外地址会被干净跳过。知道这条边界，以后遇到“这个引用到底会不会被 GC 碰”的问题，心里有底。
