## 概要

本文从一个问题出发：是否存在语言对“函数”本身进行了激进改造？沿着这个问题，讨论
逐步收敛为一个以全 meta IR bytecode 为中心、编译期与运行期共享同一套效应、分发
与缓存机制的架构设想。核心主张是：函数、类型、表达式与约束可以在 IR 层归约为统
一的项，语言特性可以由可定义的效应来构造，编译期检查器本身也是可分发的
IR bytecode 库，并通过两阶段缓存与标准接口（Comptime SDK）获得工程可行性。

### 1. 对函数本体的激进改造

类型系统的花样——依赖类型、多返回值、模式匹配——大多是在函数签名或定义方式上做
修饰，仍然保留“调用—返回”的骨架。真正拆掉承重墙的方向另有一批：续延与代数效应
（Scheme `call/cc`、Koka、OCaml 5 effects）、以消息发送替代函数调用
（Smalltalk、Erlang）、把函数降格为关系（Prolog、miniKanren）、拼接式语言
（Forth）、内容寻址（Unison）。这些方案的共同点是更换计算模型，
代价是并发语义、调试体验、性能模型与心智负担全部改变。主流语言不彻底拆函数，
不是因为想不到，而是因为换计算模型的工程代价过高。

### 2. 量、类型、执行的修饰符可以统一抽象

`const`/`var`、`trait`/`class`、`Pure`/`IO` 这三组修饰符，本质上是同一张属性表
在绑定层、类型层与计算层上的投影。一个统一的元模型是：一切皆项，每个项携带
`(type, effect, stage, capability)` 四元组，修饰符即是对四元组的约束。理论
对应物是效应系统与模态类型论。真正独立的维度可能只有两个：“它是什么”（type）
与“它能做什么”（effect），阶段与能力大多可以归约到这两者之上。

但能统一不等于该统一。分层拼写让约束的归属更清楚，默认值、检查时机、错误信息与
优化策略在各层都不同，合并成一套万能修饰符在工程上未必划算。

### 3. 一切皆变量，约束即分析规则

一个更激进的一元论主张是：函数、类型、表达式、约束全部归约为“变量”，约束只是
对变量的分析规则。这在数学上有精确对应——依赖类型论中类型本身就是项，LF 的判断
`Γ ⊢ t : T` 把类型检查形式化为上下文中的推导，纯类型系统（PTS）用 `(S, A, R)`
三元组统一了所有依赖类型语言。

但这条路会撞上三堵墙。阶段墙：若类型是运行期变量，类型检查就不可判定，依赖类型
语言靠编译期规范化绕开，代价是终止性保证的复杂化。语法墙：调用约定、栈帧布局、
闭包捕获不是“变量的分析规则”能覆盖的工程事实。约束墙：一旦约束允许任意谓词，
约束求解就退化为一般定理证明，失去可判定算法。
结论是：本体论上成立，工程上得到的是证明助手或研究语言，而非业务语言。

### 4. MLIR 式统一：框架统一，而非语义统一

MLIR 的抽象是 Operation / Value / Attribute / Region，所有方言落在同一框架内。
函数可见、栈帧可控、闭包在 lowering 中被消解、内联是 pass 而非语言特性
——这四件事在 LLVM IR、Cranelift 与各类 closure conversion pass 中早已是既成
事实。MLIR 统一的是表示载体，不是语义范畴；语言层可以保留 `fn`/`type`/`trait`
的区分，IR 层归约为项与操作，两层不必一致。

一个表面的矛盾是“栈帧可控制”与“内联自动化”的冲突。化解方式是：内联建模为编译期
效应，默认 handler 自动决策，自定义 handler 提供控制，日常使用不受影响。控制权
是可提供的选项，不是必须暴露的负担。

### 5. 效应作为语言特性的定义机制

`class` 不必是内建关键字，而可以是用户可定义的效应：包装结构、附带检查规则、
由 handler 实现布局与派发，由此衍生出 object 布局、vtable、RTTI 乃至 GC。
语言核心只剩“项 + 效应 + handler + 检查规则”，`class`/`GC`/`async`/`trait`
全部成为效应库。

已有的半路对应包括 Racket 的 `#lang`（语法层可扩展）、Koka/Eff（运行时效应）、
Lean 4（元编程定义语言特性）、可扩展编译器框架（独立 pass）。本设想的新意在于
把这些统一到“效应”这一个抽象之下：效应签名含检查规则，handler 是特性的实现。

硬点有两个。其一，检查规则在编译期执行，handler 在运行期执行，同一效应名跨
阶段，需要阶段化效应的支持。其二，效应组合后的检查规则由谁负责——组合效应的规则
能否自动推导，这是一个开放问题。若每条组合规则都需手写，“衍生”就是手工的；
若自动推导，则需要一套效应组合的规则演算，其难度比单个效应定义高一个量级。

### 6. 函数是变量、多态变量与平台特化

函数名可以绑定到多个项（SSE 版、AVX 版、标量版），由选择规则与解析阶段决定具体
项：编译期解析即静态特化，运行期解析即动态分派。对应物有 C++ `target_clones`、
LLVM function multiversioning、Rust `#[target_feature]` 加运行期检测、
Halide/ISPC。新意在于把“候选集 + 选择规则 + 解析时机”统一为多态变量的属性，
使 SSE/AVX 特化、trait 派发、重载解析都成为同一机制的实例。

卡点在于：平台特化的选择规则是约束优化而非类型合一，成本模型是编译器内部且
非标准的；ABI 一致性是硬约束，运行期解析要么强制间接调用，要么要求候选项 ABI
兼容；与效应框架组合时，又回到跨阶段与规则组合的同一堵墙。

### 7. ABI 是可协商的约定

ABI 可以降格为可协商的约定：自定义 `ccc` 与 `fastcc`，由检查规则验证调用点与
被调用点是否匹配，下至指令集全部显式化以支撑更精确的分析。LLVM 的 calling
convention 枚举早已证明调用约定在 IR 层是可标注、可检查的属性。

代价需要说清。检查规则管“能不能通”，但还需要适配规则管“怎么通”——两个约定寄存器
分配不同时，需要生成搬参、搬返回值、调栈对齐的 adapter thunk，这是约定之间的
态射，不是单个约定的属性。全显式化到指令级会让分析空间随 op 数增长，需要分层
dialect 来控制：是每层都显式，还是只有最底层显式、高层逐步 lowering 暴露，
这是一个粒度选择。检查规则、适配规则、成本模型三者各归其位，缺一不可。

### 8. IR bytecode 全 meta 分发与 C ABI 边界

全 meta 的 bytecode 使“编译或运行确定具体项”真正落地：候选项集合、选择规则、
调用约定签名、平台约束全在 meta 里，同一份 bytecode 在 AOT 链接时解析即
静态特化，在 JIT 加载时解析即运行期特化。

内部 N 个自定义约定各自适配到 C ABI 这一个公共锚点，适配规则从 O(N²) 降为
O(N)。需要注意 C ABI 实际是平台 C ABI（SysV AMD64 与 Windows x64 在 struct
返回、varargs、栈对齐上不同），封装边界需按目标平台生成 thunk；外部库内部的
ifunc 或运行期 CPU 检测是黑盒，封装声明要允许“可能多版本”。不带 meta 的动态库
构成信任边界，只保证 C ABI 层面的互操作，类似 Wasm 组件模型、P/Invoke 与 COM
的思路：富语义在边界内，窄接口在边界外。

新负担随之而来：bytecode 与 meta 的版本化、加载期对 meta 本身的验证、加载期
分析成本、跨模块 meta 可见性。这些是任何 bytecode 分发系统绕不开的标准工程
问题。

### 9. 检查器本身是 IR bytecode 库，编译时 JIT

检查规则若是数据，编译器需要一个通用解释器逐条匹配，规则一多，解释循环就是
编译期主要开销之一。把检查规则做成代码——本身就是 IR bytecode，编译时 JIT 成
本地码——就消除了解释器分派开销，其逻辑与数据库把查询计划 JIT 成机器码一致。
前提是检查规则是代码而非纯声明，这一前提在“效应签名含检查规则”的框架下天然
满足。

更大的贡献在于对称性：编译期与运行期共享同一套分发、JIT、缓存基础设施，
阶段只是解析时机而非机制分界。

新问题同样对称地出现。检查器是 JIT 后的原生代码，跑在编译器进程里，能读 IR、
写诊断、可能改 IR，因此需要一个编译期接口 ABI 或能力边界来约束它。检查器的
正确性无法自动保证——漏检放过坏程序，误检拒绝好程序——只能靠签名验证、测试与
作者责任，这与 type class 实例、编译器插件的处境相同。JIT 开销需要靠缓存摊薄。

### 10. 增量、确定性、R2R 与 Comptime SDK

增量解析的模型是：编译器负责 diff，把改动喂给检查器，检查器被动接收；需要更多
信息时向编译器请求。这样依赖追踪不在检查器作者身上，但编译器需要知道订阅粒度——
检查器注册粗粒度的关心范围，或编译器按效应签名推断。订阅粒度决定了增量精度，
这是设计取舍而非缺陷。

确定性方面，实用主义判断成立：几乎没有作者会在确定性构建里故意加入不确定的
东西。但不确定性不总是故意的，浮点舍入、哈希遍历顺序、环境变量读取都可能在作者
无意识时引入。因此 Comptime SDK 应把常见的隐性不确定源显式化——提供确定性的哈希
与遍历、标记或禁止读环境与时间——让不确定成为声明过的选择，而非意外。

R2R 即编译缓存：IR 本身是可编译单元，可直接编译成原生库，缓存键为 bytecode
哈希加目标平台加宿主接口版本。粒度较粗，一个库一个缓存单元，与 C/C++ 编译单元
模型一致，工程上可接受。缓存产物对外即 C ABI 边界。

Comptime SDK 的作用是标准化检查器与编译器的交互面：
IR 访问、诊断产出、增量请求、临时内存分配。它不是沙箱，而是标准接口——符合 SDK
的检查器可进入生态并获得增量与互操作保证，不符合的可以运行但不保证。类比 LLVM
pass 生态、rustc lint 生态、ESLint 规则生态：不限制插件能做什么，但提供标准
接口与分发规范。信任模型因此比 LLVM 更重：输入程序不可信，检查器也不可信且来自
多个作者。接受“正确性靠作者”是合理的工程选择，但需要在文档层面明确为信任声明，
避免用户误以为检查器是沙箱化的。

### 11. 两阶段编译与两个缓存点

编译流水线分两个阶段、两个缓存点：

- 阶段 1：定义 → IR bytecode。这是 bytecode 缓存，跨目标共享，与平台无关。
- 阶段 2：IR bytecode → 原生库。这是 lib 缓存，按目标配置分，多个目标变体共享
  同一份 bytecode 缓存。

这与 Roslyn 出 IL、RyuJIT 出 native code、IL 与 R2R 各缓存各的结构同构。缓存键
分两级：bytecode 键为定义哈希；lib 键为 bytecode 哈希加目标配置。改定义只失效
bytecode 及其下游所有 lib 变体；只改目标配置只失效对应的 lib 变体。

检查器走同一条流水线：检查器 bytecode 缓存一份，按目标编译出的检查器原生库按
目标各缓存一份；增量解析时运行的是当前编译配置对应的那份原生库，而非重新 JIT
bytecode。

## 当前设计状态

架构整体为：内部全 meta IR bytecode，一切皆项，效应定义语言特性，多态变量承担
平台特化与解析；编译期 JIT 检查器走同一套 bytecode 分发与两阶段缓存；增量靠
编译器推 diff；边界以 C ABI 封装，适配 O(N)；外部不带 meta 的库只保证 C ABI
互操作。编译期与运行期对称地共享分发、JIT/AOT、缓存与信任模型。

已对齐的结论包括：内联作为编译期效应，默认 handler 自动决策；ABI 可协商，
由检查规则、适配规则、成本模型三层构成；增量由编译器推 diff，检查器被动接收；
确定性靠作者自律加 SDK 显式化不确定源；R2R 是阶段 2 缓存产物；Comptime SDK
标准化接口而不沙箱。

剩余的工程决策有五项：

1. Comptime SDK 的接口边界设计：IR 访问、诊断、增量请求、能力声明。
2. 增量订阅粒度：检查器注册粗粒度关心范围，还是编译器按效应签名推断。
3. 效应组合的规则演算：跨阶段且可组合的检查规则仍是开放研究问题，倾向于以 SDK
  标准化加作者责任工程化处理。
4. bytecode 与 meta 的版本化与验证策略。
5. 全显式化与分层 dialect 之间的粒度选择。

## 关键术语

| 术语           | 含义                                                   |
| -------------- | ------------------------------------------------------ |
| 项（Term）     | 函数、类型、表达式、约束的统一表示                     |
| 效应（Effect） | 语言特性的定义机制，含签名、handler、检查规则          |
| 多态变量       | 绑定到多个候选项的变量，由选择规则与解析阶段决定具体项 |
| 检查器         | 用户可分发、编译时 JIT 的 IR bytecode 库，执行检查规则 |
| 阶段化效应     | 编译期检查与运行期处理共享效应名但分阶段执行           |
| 两个缓存点     | bytecode 缓存（阶段 1）与原生库缓存（阶段 2）          |
| Comptime SDK   | 检查器与编译器交互的标准接口，不沙箱但可预期           |
| 订阅粒度       | 检查器声明关心哪类 IR 变化，供编译器推 diff            |
| C ABI 锚点     | 内部约定各自适配到平台 C ABI，适配 O(N) 而非 O(N²)     |
